# workarounds-pure-zig.md — the earlier short-form workarounds and the pure-Zig track's W-1 … W-14 (split from workarounds.md 2026-11-23)

## Earlier workarounds (short form; expand to the full template when next touched)

- ~~**KI-4, Debug compiled at `filc -O0`.**~~ **Superseded 2026-10-01** by the KI-4 patch (full entry above); Debug is now at `-O1`. _Original why:_ Fil-C's pass segfaults on Zig's Debug IR at
  `-O1`/`-O2` (reduced to 8 `std.compress.flate` functions, `tools/p2/repro/`). Upstream defect, F1.
  _Cost:_ no inlining in Debug, which also exposes KI-13 #2 and KI-19. _Exit:_ the repro compiles at
  `-O1`.
- **KI-4, the two-line data-layout rewrite** (`ir.toFilCDialect`). _Why:_ Fil-C's LLVM is a dialect:
  `ni:0` on address space 0 plus `datalayout_after_filc`. Stock IR lacks both. System limitation.
- **KI-5, generated C-ABI entry shim.** _Why:_ `start.zig` forges pointers from integers
  (`@ptrFromInt(getauxval(AT_PHDR))`), which InvisiCap forbids by design. F2. Also hosts the panic
  handler and the `page_allocator` hook. Since 2026-10-02 the hooks live in `shim_hooks`, shared
  with a LIBRARY root for C-owns-`main` builds, and a user file's own `panic`/`os`/`std_options` are
  honoured (only `crypto_always_getrandom` is forced).
- **KI-6, target `x86_64-linux-musl`.** _Why:_ Fil-C's libc is musl; gnu-target Zig emits `*64`
  glibc names. F4.
- **KI-7, raw `syscall` asm → `zilc_syscall`** (`ir.rewriteSyscalls`). _Why:_ std makes raw syscalls
  even with `-lc`; Fil-C refuses inline asm, and a raw blocking syscall would also stall the GC
  (FUGC needs an exit before blocking). The helper goes through Fil-C's checked `syscall()`. F3.
- **KI-8, `-fno-stack-check` in every mode.** _Why:_ `__zig_probe_stack` lives in compiler-rt, which
  never goes through the pass. Safe because Fil-C checks the stack at every function entry. F4.
- **KI-9, f128 compiler-rt through the pass.** _Why:_ the helpers are not in Fil-C's libc; they are
  compiled as checked code, with every other export internalized so they cannot replace Fil-C's
  libm. F4.
- **KI-11, std overlay backport of 0.16.0 `findSentinel`.** _Why:_ 0.15.2's SIMD scan reads past the
  object (legal natively within a page). std has no hook for it. F5.
- **KI-12, `root.os.heap.page_allocator = c_allocator`.** _Why:_ `PageAllocator`'s `mmap` hint is a
  pointer at an object's upper bound. F5.
- **KI-13, overflow fold + `fromPage` patch.** _Why:_ Fil-C recovers capabilities only through plain
  integer instructions; `extractvalue` of `*.with.overflow` and integer parameters start at BOTTOM.
  Field 0 is the identical value, and the overflow branch is untouched. F2.
- **KI-14, `-fno-valgrind`.** _Why:_ Valgrind client requests are inline asm; they are no-ops unless
  run under Valgrind. F3.
- **KI-15, `sys_can_stack_trace = false` in the overlay.** _Why:_ native stack walking reads raw
  frame pointers and probes with `process_vm_readv`; it can never carry capabilities. Fil-C gives
  its own traces. F3/F2.
- **KI-17, Zig's unoptimized IR** (`--verbose-llvm-ir -fllvm`). _Why:_ `-femit-llvm-ir` is
  post-optimisation under an integral layout, so LLVM had already turned pointer loads into
  integers. F2. Side effect: exposed KI-18 (globals no longer folded away).

## The pure-Zig track: W-1 … W-14 (W-1…W-10 first written in zailc, 2026-10-08/09, brought here 2026-10-27; W-11…W-14 zilc's own)

The track (`roadmap.md` Z1) came from zailc with its workaround notes; the code cites them by these
numbers, so they live here too, condensed. zailc's `cmem/workarounds.md` keeps the long forms.

- **W-1. The generated banner still names the Ruby script.** `filc_native.h` and
  `filc_native_forwarders.c` from `zilc-gen` begin `/* Generated by generate_pizlonated_forwarders.rb */`.
  _Why:_ the proof of the port is byte-identity with Ruby's output, and the banner is part of the
  bytes; no consumer reads it. Exit: when zilc stops comparing against Ruby.
- **W-2. Zig's caches stay out of the repo.** The checkout is on exFAT under `/mnt/d`;
  `tools/lib/tool.ts` `zigCacheArgs()` puts both caches in the Linux home (zilc's KI-2 rule).
- **W-3. `-nostdinc` also drops Zig's bundled clang headers.** Upstream pairs it with
  `find_clang_include_dir.rb`; `build/pure_zig.zig` adds `-isystem <zig lib>/include` instead. A
  relative: any Makefile pairing `-nostdinc` with a probed compiler include dir.
- **W-4. `verse_heap_chunk_map_entry.o` lacks the `pas_panic` reference upstream's has.** A compiler
  difference (an assert or unreachable path Zig's clang 20.1.2 folds and Fil-C's 20.1.8 keeps;
  surmised). Defined symbols are equal. Ratcheted in `verify-libpas.ts` `KNOWN_UNDEF_DIFFS`.
- **W-5. ✅ Fixed: the `musl-headers` step was cached by its arguments, not by the musl tree.**
  `musl_headers.inputs()` is the one list `install` reads, and `build/pure_zig.zig` declares each
  entry as a file input, so an edited or added header reruns the step (proved and inverted in zailc).
- **W-6. Zig passes absolute source paths, so `__FILE__` would not be upstream's.** Upstream's make
  runs in `libpas/` and names `src/libpas/x.c`; `-ffile-prefix-map` maps ours back
  (`../filc/main/main.c` for the crt objects, `yolounwind.c`). Guarded by the oracles' form rule.
- **W-7. Fil-C 0.686: `landing_pad_impl` asserts `can_catch` when an inlined destructor writes a
  global** (C++ at `-O1`). An upstream defect, found and reduced in zailc
  (`../zailc/tests/link/eh_dtor_writes_global.cpp`, `../zailc/UPSTREAM-ISSUES.md`). ⏳ Not yet
  re-checked on 0.687: carried to the next Fil-C update (owner, 2026-11-06; `upstream.md` Stage A
  step 8), unless the link-and-run item reaches it first.
- **W-8. What GCC (upstream's release) and Zig's clang emit differently.** Upstream built yolo musl
  with GCC 12.3 and compiler-rt with GCC 11.4; zilc's pure-Zig build uses Zig's clang. Defined
  symbols are equal; only these UNDEFINED differences are allowed, each set in its oracle with an
  exact count: GCC's explicit `_GLOBAL_OFFSET_TABLE_`; clang's `memcpy`/`memset` calls where GCC
  inlines (both defined by this libc); Ubuntu GCC's `__stack_chk_fail` and `__fprintf_chk` (⚠️
  2026-11-05: these two are NOT compiler differences but Ubuntu GCC's default
  `-fstack-protector-strong` / `-D_FORTIFY_SOURCE=2`; since 2026-11-05 zilc passes them, and what
  remains is C-10 / C-11 in `cmem/toolchain-quirks.md`); each
  compiler's own helper libcalls (`__divti3` vs `__udivti3`, `__gttf2`/`__letf2`/`__floatsitf` vs
  `__lttf2`); and one empty translation unit (`src/linux/cache.c`) that only GCC gives a compile
  unit. Lasts as long as the oracle is a GCC-built release.
- **W-9. A Windows path forwarded into WSL broke CMake under `zig cc`.** Cannot recur in zilc: since
  2026-10-27 its tools refuse to run outside Linux, so nothing is forwarded from Windows.
- **W-10. Fil-C's `_Float16` conversions use the wrong register in the release's libyolort.** The
  release's compiler-rt was built by GCC 11.4, for which compiler-rt's CMake leaves
  `COMPILER_RT_HAS_FLOAT16` off: its two `_Float16`-only members are empty, and `__extendhfsf2` /
  `__truncsfhf2` read an integer register where LLVM's callers (Fil-C's clang) pass an SSE one, so
  `float` → `_Float16` → `float` is wrong (measured in zailc on 0.686: `1.5` → `0.00830078`). zailc
  FIXES it, as its recorded departure, by letting the probe succeed under Zig's clang. **zilc does
  not depart** (owner, 2026-10-27: faithful, zailc keeps its modifications): the importer sets
  `-DCOMPILER_RT_HAS_FLOAT16=OFF`, as the release had it, and `verify-compiler-rt.ts` allows no
  extra definition (budget 0). So zilc's pure-Zig libyolort carries upstream's defect, as the
  release does; it is upstream's to fix. Re-check per release: if upstream builds libyolort with a
  `_Float16`-capable compiler, the oracle's member set changes and says so.
  **0.687 (2026-10-27): still the case** — the release's libyolort is `GCC: (Ubuntu
  11.4.0-1ubuntu1~22.04.3) 11.4.0` (`.comment`) and its `extendhftf2` / `trunctfhf2` members define
  nothing. The probe's variable is per architecture: `COMPILER_RT_HAS_x86_64_FLOAT16` (it adds
  `-DCOMPILER_RT_HAS_FLOAT16` to the flags; the members test that macro). A first try with the
  unsuffixed `COMPILER_RT_HAS_FLOAT16=OFF` changed nothing, and `verify-compiler-rt.ts` failed on
  exactly the two definitions — the oracle catching the departure it exists to catch.
- **W-11. Linking `libyoloc.so` (the loader) with Zig's LLD instead of GCC's driver and GNU ld**
  (zilc's own, 2026-10-27; zailc never built the shared half). Three parts:
  1. _`zig cc` refuses two of musl's link flags._ Symptom: `unsupported linker arg:
     --exclude-libs` / `--dynamic-list`. These are two of configure's seven `LDFLAGS_AUTO`, which
     `import-yolomusl-sources.ts` reads into `ld_args`. Fix: `build/pure_zig.zig` runs `zig ld.lld`
     (Zig's LLD) directly with upstream's link rule spelled out (`-shared -e _dlstart`, plus
     `--build-id=sha1 --eh-frame-hdr -z relro`, which GCC's driver adds). Ruled out: dropping the
     flags, which would change the export set.
  2. _`--exclude-libs=ALL` means something else here._ Symptom (measured): the first link exported
     **8** symbols where the release exports 1,653, and so every program's link listed every libc
     symbol as undefined (that output then crashed the gate with `StderrStreamTooLong`, fixed by
     raising its capture limit). Root cause (measured): upstream links the `.lo` objects loose, so
     its only archive is `$(LIBCC)` and `ALL` hides only the compiler runtime; zilc links yolo musl
     as `--whole-archive libyoloc.a`, so `ALL` hid libc too. Fix: `--exclude-libs=libyolort.a`,
     upstream's effect named exactly. Proof: 1,653 exports equal by name and type, 0 undefined.
  3. _Two segment kinds differ, allowed by name in `verify-yolomusl.ts`._ Measured: zilc's has a
     `PHDR` segment, which LLD gives a shared object and GNU ld does not; the release has
     `GNU_PROPERTY`, which GNU ld makes from `.note.gnu.property`, carried by all 1,343 of the
     release archive's GCC-built members (x86 ISA-used notes) and by none of Zig's clang's. The
     dynamic tags are equal. Neither difference changes what the loader does: gate 8/8, corpus
     78/78 as designed and output comparison 0 unexplained with it linked (`testing.md`). Lasts as
     long as the oracle is a GCC/GNU-ld-built release. A relative: any other set that differs
     between GCC/GNU ld and clang/LLD output (W-8 is the symbol-level family).
- **W-12. libpas whole: the Fil-C half and `libpizlo.so` without the host's clang** (2026-10-30;
  owner: "complete the libpas part"). Upstream's `libpas/Makefile` compiles the stock half with
  `HOST_CLANG` (Ubuntu clang 14 for the release), `filc/src/*.c` with Fil-C's clang, and LINKS the
  four `libpizlo.so` through `HOST_CLANG` (`$(SHLD) … $(SHLDPOST)`). `build/pure_zig.zig`
  (`buildLibpizlo`, `-Dfilc-clang`): the four object sets (release/test ×
  default/gc-verify settings, `filc_dynamic.c`; `filc_static.c` for `libpizlo.a`); the Fil-C half
  by the given clang with `-O3 -g -W -Werror` and `-ffile-prefix-map=<src>/=../` (W-6); the links
  by `zig ld.lld` with what the release's driver added (`--build-id=sha1 --eh-frame-hdr -z relro
  --hash-style=gnu`, measured on the release's), crti/crtbegin … libyolort.a `-lyoloc -lyolom`
  crtend/crtn, objects as `--whole-archive`. Two traps: (1) the Fil-C clang reads
  `stdfil-include` and `os-include` from ITS OWN tree's `pizfix/` (`-v` shows the search list), so
  the tree must have them before the compile; (2) `-dynamic-linker` on a shared object gives LLD an
  INTERP the release lacks — left out. Proof: exports equal for all five artifacts (`testing.md`).
- **W-13. `zig cc` as the host compiler for upstream's own scripts — measured, NOT adopted**
  (2026-10-30; owner asked whether a `cc` alias could redirect the GCC steps to Zig). An alias
  directory first on PATH (`cc gcc clang c++ g++ ar ranlib` → Zig) needs, found by failing:
  (1) no `-target` — with one, `zig cc` ignores `/usr/include` and projeny's `<curl/curl.h>` is not
  found; use the native target with `-mcpu=baseline`; (2) drop `-Wl,--dependency-file=` (CMake 4),
  "unsupported linker arg"; (3) `-fno-sanitize=all` — `zig cc` turns UBSan on when no `-O` is given,
  so compiler-rt's `crtbegin.o` (compiled without `-O`) called `__ubsan_handle_*` and the user
  libc's link failed; (4) alias `clang` too — yolounwind and libpas's stock half call it by name;
  (5) `-march=x86-64-v2` (libpas) reads to Zig as CPU `x86` with features `64`, `v2` removed
  ("unknown CPU: 'x86'") — needs `-mcpu=x86_64_v2`. And one it CANNOT fix: musl's `configure`
  tests each link flag and silently drops `--exclude-libs` and `--dynamic-list`, which `zig cc`
  refuses, so `libyoloc.so` links with **503** self-binding relocations where the release has
  **21** — exports identical (1,653), so a symbol check does not see it. Hence the zig chain uses
  `zig build pure-zig` for every stock piece (faithful, verified) and upstream's scripts only for
  the steps Fil-C's clang does (`tools/filc/build-filc-from-source.ts` MODE=zig).
- **W-14. LLD has no `.plt.got`: 5 more `JUMP_SLOT`s in `libpizlo.so` than GNU ld makes**
  (2026-11-04; owner: "review and test … scope the fix … to bring it into parity"). A function both
  called through the PLT and loaded through the GOT (the weak `__register_frame_info` /
  `__deregister_frame_info` / `__cxa_finalize` in compiler-rt's `crtbegin.o`, tested before each
  call; two `pas_bootstrap_free_heap_*` functions libpas both calls and takes the address of) gets
  from GNU ld a `.plt.got` stub jumping through its one GOT slot (`GLOB_DAT`), from LLD a regular
  PLT entry with its own `JUMP_SLOT` as well. Measured on identical objects (2,134 vs 2,139); the
  zig chain's objects linked by GNU ld equal the GCC chain's library exactly (`testing.md`). No
  behaviour difference: both resolve to the same definition (yolo musl's loader binds at load).
  Fix, if parity is wanted: link with GNU ld (scope in `open-work.md`); LLD 20 has no option for it.
  **Owner, 2026-11-05: not wanted — keep LLD** (_"We are looking for the end result being the same.
  Not specifically that the end compilation product is the same."_; `design-decisions.md`).
  A relative: W-11 part 3 (`PHDR`), another LLD-vs-GNU-ld layout difference.
